# Harness configuration (`.agents/` canonical; harness directories are adapters)

Agent-facing content lives in **`.agents/`**, harness-neutral, mirroring the
`CLAUDE.md → AGENTS.md` symlink pattern. Harness-specific registration stays
in its native adapter directory.

**The rule: how a harness *discovers* a thing decides how it gets wired.**

| Kind | Discovery | Wiring | Example |
| --- | --- | --- | --- |
| Skills, subagents | Harness scans a well-known directory | Project-authored content lives in `.agents/`; Claude follows a symlink and Codex reads it directly | `.claude/skills → ../.agents/skills`, `.claude/agents → ../.agents/agents` |
| Project hooks | Harness takes an explicit path from a config file | Project-authored scripts live in `.agents/hooks/`; adapters register paths to them | `${CLAUDE_PROJECT_DIR}/.agents/hooks/…` |
| Tool integrations | A tool owns native setup recipes and lifecycle behavior | Keep its generated files in the native locations and validate them with the tool | `bd setup codex`, `bd setup claude`, `bd setup factory` |
| Root instruction file | Harness reads a fixed filename | `AGENTS.md` is canonical; the Claude-specific name is a symlink | `CLAUDE.md → AGENTS.md` |
| Per-user / runtime state | Harness writes it | Real file in the owning adapter, gitignored, never mirrored | `.claude/settings.local.json`, `.claude/.bandwidth/` |

Git tracks exactly three things under `.claude/`: the two symlinks and
`settings.json`. Beads owns its marked sections, `.agents/skills/beads/`, and
its entries in the tracked `.codex/` integration files; regenerate those with
`bd setup`. Project hook registrations are generated by
`python3 .agents/hooks/install-codex-project-hooks.py`, which preserves Beads
and unrelated hooks. Run it after `bd setup codex`; do not hand-edit the
generated `.codex/hooks.json`.

After loading changed Codex hooks, review and trust their definitions through
`/hooks`. Codex skips untrusted definitions; registration checks establish
configuration coverage, not approval in the running application.

`scripts/checks.sh harness` enforces the table — broken symlink, symlink
escaping `.agents/`, missing/non-executable project hook path, a reappeared
`.claude/hooks/`, stale Beads integration, or a doc citing a `.claude/` path
that isn't tracked all fail the stage. It runs first in `.githooks/pre-push`
and as its own CI step.

## Layout

- `.agents/skills/` — [agentskills.io](https://agentskills.io/specification)
  standard layout. Codex discovers it directly; Claude Code follows the
  `.claude/skills` symlink. The `beads` skill is generated by `bd setup codex`.
- `.agents/agents/` — subagent definitions (Markdown + frontmatter),
  symlinked from `.claude/agents`.
- `.agents/hooks/` — standalone shell scripts speaking the shared JSON hook
  protocol: a payload on stdin (`session_id`, `transcript_path`, `tool_name`,
  `stop_hook_active`, …), decisions via exit code / stdout JSON. The scripts
  are the portable asset; registration is the adapter. Each `stop.d/` check
  is independently testable:
  `echo "$payload" | .agents/hooks/stop.d/20-commit.sh; echo $?`
  (exit 0 = pass, exit 10 = fire with the reason on stdout).
- Beads context is supplied by its native adapters: `bd codex-hook` under
  `.codex/` and `bd prime --hook-json` in `.claude/settings.json`. AGENTS-aware
  harnesses consume the full managed Beads section in `AGENTS.md`; other
  harnesses should use their `bd setup <recipe>` integration or `bd onboard`.

## `ffxi-agent/` is a separate, intentional exception

`ffxi-agent/` ships its own `.claude/{hooks,agents,skills,settings.json}`
as *real* directories, plus an `opencode.json` that reads a `.claude/`
path. That is not drift: it is the runtime playbook for an LLM agent
*playing the game*, shipped as a unit, with a different audience from this
repo's dev harness. It is out of scope for the table above, and
`scripts/checks.sh harness` skips it.
